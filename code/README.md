# The witnessed gate

This Python library implements the design specified in `../model/Gate.tla` and checked with TLC. Before an AI agent's tool call starts, the gate writes it in a journal, sends the entry's fingerprint to a separate witness process, and waits for a signed stamp naming that fingerprint. Only with a valid stamp does it write "approved" and let the call start. It supports one witness or two witnesses with fixed main and backup roles.

The repository root contains `code/`, `model/` and `results/`. Paths below are relative to `code/` unless they describe files created during a run.

## Setup and tests

Use Python 3.11, PyNaCl 1.6 and `inspect_ai` 0.3.291. Install the dependencies with your Python environment's package installer:

```sh
python -m pip install 'PyNaCl~=1.6.0' 'inspect_ai==0.3.291'
```

From `code/`, set `TMPDIR` to a folder outside the repository and run:

```sh
test_tmp_dir="$(mktemp -d /tmp/witnessed-gate-tests.XXXXXX)"
TMPDIR="$test_tmp_dir" python -m unittest discover -s tests/unit
rm -rf "$test_tmp_dir"
```

The suite contains 228 tests and takes about 70 seconds. It uses no network, API key or real model. Inspect tests run the demo in a subprocess with `HOME` set to a temporary folder because Inspect creates a data folder under `~/Library/Application Support`.

## Each step in the code

| Gate.tla | Code | What happens |
|---|---|---|
| `Propose(a)` | `Gate.propose` | The call exists only in the gate's memory. |
| `WriteInJournal(a)` | `Gate.write_in_journal`, `Journal.write_record` | One record line is written and fsynced. |
| `SendFingerprint(a)` | `Gate.send_fingerprint` | Refuses to send unless the record line is in the journal. Sends once to each witness it asks. A send that fails counts as a lost message. |
| `WitnessStamps(f)` | `WitnessStore.stamp` | Appends the fingerprint to the chain, fsyncs the log, then signs and returns the stamp. A fingerprint already held gets the stamp it got the first time. |
| `StampArrives(f)` | `Gate.stamp_arrives` | Takes a reply only for a request this gate sent, on the channel it went out on, and a stamp only from the witness pinned in the slot it was sent to. Checks the signature under that witness's pinned key, then that the stamp names this fingerprint. Takes it only while its call waits; a stamp for a refused call changes nothing. |
| `Run(a)` | `Gate.run` | Needs a held stamp. Writes "approved" with the stamp, fsynced; the caller then starts the tool. If that write fails or may have failed, the gate stops as after a crash (`GateCrashed`). |
| `GiveUp(a)` | `Gate.give_up` | At the time limit, or at once when no witness it asked can still answer. Writes "refused". With two witnesses only while the gate holds no stamp for the call, as both two-witness models say; with one, `Gate.tla` lets it give up at any moment while the call waits. |
| `GateCrash` | recovery in `Gate.__init__` | Runs only when a gate opens a journal that already has lines, before it takes a call; `recover()` called later raises. Writes a "restart" line listing the undecided records, then a refusal for each. A failed or uncertain journal write is a crash as well: the gate stops, and the next gate's recovery decides what is left. |
| `WitnessCrash` | killing a witness process and starting it again on the same folder | `WitnessStore` reloads its saved list; the key and the chain stay the same. |
| `LoseFingerprint`, `LoseStamp` | a witness down, or `faulty_witness` modes `drop` and `outage` | |
| (no step: two witnesses) | `Gate.catch_up`, `Gate.settle` | A later stamp for a call that ran is journaled as `second_stamp`; a witness that missed fingerprints is sent them when it answers again, and a request it left unanswered past its wait is sent again once it answers anything later. |

## Each check at runtime

`checker.check_run` reads the record file, the decision file, each witness's log and the effects file, and re-derives every fingerprint, chain link and signature. It takes the witnesses' keys from the journal's open line unless keys kept outside the run are given (`trusted_keys`, with `witness_keys` as an alias; `BenchLedger.public_keys()` supplies these keys). Without such keys a pass shows that the run's files agree with one another; someone who replaced all of them with a new key and freshly signed history would pass too. The rules apply to each witness on its own.

| Check | What the checker tests |
|---|---|
| `journal` | Record fingerprints, record ordering and links, decision ordering and links, schemas and pinned witness identities are valid. |
| `witness_log` | Each witness's chain links and signatures verify, and no fingerprint appears twice. |
| `Rule1` | At least one witness holds each started call's fingerprint before the call starts: the log of the witness whose stamp let it run holds it, with that stamp. An effects line with no record, a second effects line for one approval, and an effects line for a call never decided all fail. |
| `Rule1Step` | Each effects line comes after that witness logged the call's fingerprint. |
| `Rule2` | Every stamp in the journal is also a signed head of its witness's chain (its size is its index plus one). Each signed head must match that witness's log at its size, and each must extend the one before it. A removed or rewritten entry fails when a retained stamp or a signed head kept outside the run covers it; an entry cut from the tail of a log, for a call whose stamp the gate never kept, passes unless a signed head kept outside the run covers it. |
| `Check3` | Every fingerprint in every witness's log is a record in the journal. |
| `RunNeedsHeldStamp` | Each approval holds a valid stamp for its record, received before the approval was written and before the tool's effects line. |
| `RefusedNeverRuns` | No effects line for a refused call, and no record that is both refused and run. |
| `JournalBeforeSend` | Each record line was written before any witness logged its fingerprint. The unit test `JournalBeforeSend` also checks this directly: an observing witness reads the journal file when each fingerprint arrives. |
| `CrashRefusesUndecided` | Each restart line lists exactly the records undecided before it, and each of them is refused after it, before any newer record is decided. |
| `StampsComplete` | Two witnesses only. Every second stamp is valid and in its witness's log. With `catch_up_done=True`, every started call must also hold the stamps its mode requires: both witnesses' in "both" mode, the main witness's in "failover" mode. |
| `StampsOnlyFromAsked` | Each stamp names a witness permitted by its own journal's pins. Requests, channels and failover send timing are not recorded, so the model's stronger condition that the witness was asked is unmeasured. |
| `effects` | Version 2 schemas, unique execution identities and one execution per approval bind effects to the exact record, function and argument hash. |
| `arguments` | Checker argument forms, journal filenames and the expected mode are valid; unreadable forms are reported as problems. |
| `DecisionHeads` | At close each running witness saves a signed `decision_head` entry, an anchor: the journal's identity (sha256 of its open line), the decision chain's length and the hash of its last line. Every anchor of a journal, in any given witness's log, required or not, must match the chain at its own length. A mismatch fails and names the witness and the length; so does an anchor longer than the chain, since lines were removed, and an anchor whose journal matches no given decision file, since a rewritten open line changes the identity. For each required witness, and a failover backup whose stamp a decision holds, the lines after its longest anchor go under `unmeasured` as `decision heads`, with their count; so do, for each restart line, the lines before it that the witness never anchored before that restart, with their range. A decision head given in `signed_heads` whose signature verifies is compared with the chain in the same way; it counts neither as an anchor nor as a kept head. An anchor counts for a restart only if its signed time `t` is earlier than the restart line's `wall_ns` (deviation 13). |

**Kept heads.** A head given in `signed_heads` covers the tail of a log only if its kind is `head`. A stamp or a decision head given there is refused as a kept head, with a note, because anyone holding the log can rebuild one; the log then counts as having no kept head (`signed_heads` under `unmeasured`). Such an item is still checked against the log, as the stamps held in decision lines are. A decision head given there is also compared with the decision chain, as an anchor in a log is, and a contradiction fails `DecisionHeads`.

**Failover and a main witness down at close.** The main witness is required and the backup is not, unless a decision holds the backup's stamp. If the main is down at close, only the backup anchors. The main's missing anchor puts `decision heads` under `unmeasured`, so the run is `pass_incomplete_evidence`. The backup's anchor is still compared, and a decision file it contradicts fails `DecisionHeads`.

**What the time checks show.** `Rule1Step`, `RunNeedsHeldStamp` and `JournalBeforeSend` compare `time.time_ns()` values taken before the line they sit in is written and synced: a record's `wall_ns` before its write, a witness's `t` before its log line is saved. They show the order in which the steps began. The unit test `JournalBeforeSend` shows that the record line was visible in the file when the fingerprint arrived. Neither shows that a line was durable on the drive before the next step; measuring that would need the end of each sync timed, which no file records.

The report also lists, in `calls_missing_stamps`, every started call that still lacks a required stamp, and, in `only_one_witness_holds`, every fingerprint that only one witness's log holds. The checker also checks an inclusion proof against a chain (`verify_inclusion`) and that one signed head extends another (`verify_append_only`); the witness serves both proofs (`proof` and `consistency` requests).

## Two witnesses

Two witnesses are an experiment, exploring what to do when one witness is down. One witness is the core design; the modes below apply only when two witnesses are configured.

Each witness is its own process with its own Ed25519 key, and the journal's open line pins both keys and the mode.

- **"both"**, the default with two witnesses: every fingerprint goes to both witnesses at once, and the call runs on the first valid stamp. The other stamp is journaled as `second_stamp` when it comes. A witness that missed fingerprints, because it was down or did not answer, is sent every approved fingerprint it has not stamped once it answers again, so the catch-up runs both ways. A request it left unanswered past its wait is sent again once it answers anything later; the witness returns the stamp it gave the first time. After the catch-up every started call holds both stamps, so forging an entry takes both keys. `close(grace)` reports whether that point was reached (`CloseReport.catch_up_done`).
- **"failover"**, a setting for comparison: the fingerprint goes to the main witness, and to the backup only if no valid stamp comes within the wait. The catch-up runs towards the main witness only. Entries stamped in normal running sit in the main witness's list alone.
- Either way, a valid stamp from either witness counts, nothing runs without one, deletions included, and a call is refused, with the refusal journaled, when no witness gives a valid stamp in time or a gate-side policy rejects the attempted call.
- Each witness keeps its slot. A gate refuses one client in two slots, two witnesses with one id, and two with one key. If the main witness cannot start, the journal pins its slot as empty, the backup stays the backup, and the gate and the ledger report themselves as degraded.
- One witness stays a supported setting: pass one client, or no `backup` to the ledger, to compare one-witness and two-witness operation.

## Where the code differs from the spec, and why

1. **Run is two steps.** The spec writes "approved" and starts the tool in one step. The code fsyncs the approval, and Inspect starts the tool after the approver returns. A crash between the two leaves an approval with no effect; the checker lists these. The order is the safe one: no effect without an approval on disk.
2. **The gate gives up early when nothing good can arrive:** every witness it asked is unreachable, has stopped, has answered with an error, or has sent a stamp that fails its checks. The spec lets the gate give up at any moment while it waits, so this is one of the spec's orders.
3. **A crash and a restart are two events.** Recovery runs only when a new gate opens the journal, before it takes any call. `recover()` on a gate already open raises, because its live calls and held stamps would outlive recovery. A recovery cut short leaves its records undecided, and the next start refuses them; `RecoveryOnlyAtOpen` tests that case. A failed or uncertain journal write is also treated as a crash (deviation 10).
4. **The journal is ordered and chained, in two files** (see the interface below). The spec's journal is a set of entries and leaves order and chain to the code. The code adds the kinds `open`, `restart` and `second_stamp`. The record file holds one line per action, so that the bench's planted edits, which work by line position, apply unchanged.
5. **The stamp is not in the record line.** A record line is written before its fingerprint goes out, so its stamp cannot exist yet. The record format keeps `receipt` null; the stamp is in the record that `write` returns, in the decision file and in the witnesses' logs.
6. **Messages.** A pipe neither loses nor repeats a message by itself. Loss means a witness is down; late means a slow witness; the gate never sends one fingerprint twice to one witness, outside the catch-up; a repeated fingerprint gets the same stamp. The catch-up does send one again: a request left unanswered past its wait counts as lost once that witness has answered anything since, which is how the spec's lost message looks from the gate; a channel that has gone quiet gets no repeats. A reply counts only on the channel and from the witness its request went to, and request ids carry a connection generation, so a late reply from a restarted witness's old process cannot be matched to a new call. Sends go through a writer thread with at most 64 queued messages and one pipe write per witness; a full queue rejects a send immediately as a lost message. The spec lets any message repeat at any time, which the code cannot produce. The fault modes cover the other cases.
7. **Fingerprints and stamps are real:** sha256 and Ed25519 where the spec has labels. The record fingerprint is sha256 of the canonical JSON of the line without `fp` and `receipt`, and the line holds a random 16-byte `salt`. So the hash covers the salt inside the canonical bytes, and compatible record checks can still recompute it.
8. **One call at a time,** by a lock that every public step and lifecycle method takes, with the call's state checked again inside it. The spec lets the three actions overlap at every step; the code has fewer orders than the spec checked, which is the safe direction for these rules. Each journal and each witness folder also has one owner at a time: exclusive locks on both evidence paths (record and decision file, each with `.lock` appended after resolving symlinks) and on the witness's `DIR/lock`, held for the owner's life, so a second gate or witness process fails at once. Names such as `run` and `run.jsonl` cannot share a decision stream concurrently. Runs that are to share a witness log take turns on it; no shared witness service is built.
9. **Times.** `Rule1Step`, `JournalBeforeSend` and `RunNeedsHeldStamp` compare `time.time_ns()` values from several processes on one machine. A clock that steps backwards could raise a false alarm. The restart rule of `DecisionHeads` compares a witness's `t` with a restart line's `wall_ns` in the same way; there a clock step can turn an honest pass into `pass_incomplete_evidence` (deviation 13). Each value is also taken before the write and sync it sits beside, so these are checks of the order the steps began in and of what the files showed (see "What the time checks show").
10. **Storage.** The spec assumes perfect storage. The code fsyncs every line; on macOS `fsync` does not empty the drive's own cache, and `full_fsync=True` uses `F_FULLFSYNC`, which does, at a cost in time. A last line without its newline is cut when a file is reopened, because its write never finished and nothing depended on it. `full_fsync` reaches both witnesses through the ledger and the approver (`--full-fsync`), and the witnesses' hello lines, the pins and the open line record it. Any error while a journal line is written or synced poisons the journal, since the line may be on disk in part or in full: the gate stops as after a crash. Before durable approval the caller receives `GateCrashed` and no permission. Once approval is durable, a catch-up storage failure is returned in `Decision.catch_up_error` and its reason; that approval remains valid, and every later operation raises `GateCrashed`. Nothing more is appended, and the next gate's recovery decides any undecided call. For a failure before permission reached the caller, recovery refuses the call if its decision line never reached the file; if the approval line did reach it, an approval can remain with no effect (deviation 1). A post-approval catch-up failure leaves the durable approval valid. A witness whose log write fails answers every later stamp request with an error. A restart reloads, validates and synchronizes the recovered log at the requested durability before serving any stamp or signed head; startup fails if that sync fails.
11. **Each witness's key is a file** in its folder, mode 0600. The gate does not read the private key. An operator with access to both witness folders can read both keys. The spec takes stamps as impossible to forge, which here holds only against an operator who cannot read those folders. The agent's own tools count as such an operator: the witnesses run as the same user as the gate and the eval, with no separate OS identity or file isolation, so an approved shell or file tool that can read those folders can read both keys and sign stamps. The measurements hold only for tools that cannot reach the witness folders; isolating the keys would take a separate user or machine for each witness.
12. **Which model each setting follows.** One witness follows `../model/Gate.tla` with `../model/Gate.cfg`; TLC found no error in 321,510 distinct states (`../results/outputs/1_Gate.txt`). The default two-witness "both" mode follows `../model/GateBothWitnesses.tla` with `../model/GateBothWitnesses.cfg`. The current design has **4,207,410 distinct states**, with no error in its safety run (`../results/two_witnesses/matrix_receipts/x1_GateBothWitnesses.txt`). Its configuration uses two calls and at most one crash of the gate and one of each witness, with `TypeOK`, `Rule1`, `Check3`, `RefusedNeverRuns`, `StampsOnlyFromAsked`, `BothListsHoldStarted` and `BothReceiptsHeld` checked in every state and `Rule1Step`, `Rule2`, `RunNeedsHeldStamp`, `CrashRefusesUndecided` and `JournalBeforeSend` over steps. Individual checks against faulty variants are in `../results/two_witnesses/matrix_receipts/matrix.md`. The comparison mode "failover" follows `../model/GateTwoWitnesses.tla` with `../model/GateTwoWitnesses.cfg`; its own checks pass, but `../model/GateTwoWitnessesBothLists.tla` shows that it violates `BothListsHoldStarted`. Catch-up is covered by `BothListsHoldStarted` and `BothReceiptsHeld` in finished states: both witnesses are up and all catch-up is done, so both lists hold every started call and the gate holds both receipts. The safety run does not establish eventual catch-up as a liveness property; `close(grace)` reports whether it finished. With two witnesses, `give_up` refuses only while no stamp is held (`GiveUp` requires `~HoldsStamp(a)` in both two-witness models); one witness follows `Gate.tla`, which allows giving up with a held stamp. The code's catch-up in `decide` asks only witnesses that answered on their current channel. An unanswered request remains on its way until its wait ends and its witness answers again, while the model may send whenever no copy is on its way. Storage errors stop the gate as a crash; recovery applies `CrashRefusesUndecided` (deviation 10).
13. **Anchors are made at close, and an anchor request carries no authentication.** The checker compares every anchor with the decision chain at its length, and counts as unmeasured the decisions a witness never anchored before a restart. This stops a forger who only edits files. "Before a restart" is determined by the clock: an anchor counts for a restart only if its signed time `t` is earlier than the restart line's `wall_ns`. An anchor made at or after the restart is still compared with the chain, and still counts for the lines after the witness's longest anchor. When the run is closed after the restart, its final anchor covers the restart line, `wall_ns` included, so that time cannot be changed afterwards without failing `DecisionHeads`. **The clock model.** `t` and `wall_ns` are `time.time_ns()` readings on one machine, the model `JournalBeforeSend` already uses (deviation 9). In an honest run the gate asks for anchors only at close, each of the whole chain it holds, so every anchor a restart can count was made before that restart. A clock step can only push an honest run to `pass_incomplete_evidence` under this rule, never to a false pass: a step back between a close and the next restart can make that close's anchor look later than the restart, and the lines it covered are then reported as not anchored before it. The rule trusts the clock as `JournalBeforeSend` does; someone who could set the machine's clock back after a restart could make an anchor obtained after it look earlier. **The remaining limit.** What still passes is an anchor obtained while the gate is down, before the restart line is written: an operator who can send messages to a witness then can ask it to anchor a rewritten chain, since anchor requests carry no authentication. Binding each decision at a witness when it is made would close that gap. That is a separate design option, not built here. The cost of the restart rule: an honest crash and restart is `pass_incomplete_evidence`, because the decisions before the crash were never anchored before the files were within the operator's reach.

## Interface

### Files and messages

The repository root contains `model/`, `results/` and `code/`; paths in this README are relative to `code/`.

- **Record file `<name>.jsonl`.** One line per action. The caller's fields are kept as given, and the journal adds `seq` (0, 1, ...), `prev_fp` (`""` first, then the previous line's `fp`), `salt`, `wall_ns`, `action_kind`, `receipt` (null) and `fp`. Inspect records carry `call_id`, `tool_call_id`, `function` and `arguments`. Bench records carry `run_id`, `t`, `handover`, `labels`, `verdicts` and `decision`.
- **Decision file `<name>.decisions.jsonl`.** Each line has `seq`, `prev` (sha256 of the previous line's bytes, 64 zeros first), `kind` and `wall_ns`. The first line is `open`, with `format`, `witnesses` (main first), `witness_mode`, `witness_operator`, `routes`, `wait_seconds`, `backup_wait_seconds` and `full_fsync`. Each witness pin has `witness_id`, `pubkey`, `role` and `full_fsync`; a witness that never started is pinned as `{"witness_id": null, "pubkey": null, "role": ..., "missing": ...}`. `approved` and `second_stamp` lines have `record_seq`, `record_fp`, `stamp` and `stamp_received_ns`; `refused` has `record_seq`, `record_fp` and `reason`; `restart` has `records_seen` and `undecided`.
- **Witness log `<witness dir>/log.jsonl`.** A stamp entry has `index`, `fp`, `prev_head`, `head` = sha256(`prev_head` + `fp`) over the hex strings, starting from 64 zeros, `t`, `witness` and `sig`. Decision-head entries anchor a journal identity, decision-chain length and decision hash in the same witness chain. Inclusion and append-only proofs span both kinds of leaf. Stamp-only logs remain readable, with incomplete decision evidence.
- **Signatures.** A stamp is `{kind: "stamp", witness, fp, index, size, head, t, sig}`, with `size` = `index` + 1. A terminal signed head is `{kind: "head", witness, size, head, sig}`. `sig` is Ed25519 over the canonical JSON of the message without `sig`. Canonical JSON uses sorted keys, separators `,` and `:`, and UTF-8.
- **Effects file.** Each execution writes a version 2 line with `call_id`, `exec_id`, `record_fp`, `function`, `args_sha256` and `wall_ns`. `call_id` is display metadata only; exact execution binding is described below.

### Gate

`Gate(journal_path, witness=None, witness_pubkey=None, wait_seconds=2.0, operator=..., routes=None, full_fsync=False, witnesses=None, witness_keys=None, backup_wait_seconds=None, witness_mode=None)` accepts either one `witness` or `witnesses=[main, backup]`. Two witnesses default to `"both"` mode. Use None for a slot whose witness is down: `Gate.slots` holds the fixed slots, while `Gate.witnesses` holds only connected clients. A gate raises `GateError` for one client in two slots, two clients sharing an id or key, or pins sharing an id or key. A reopened journal keeps its pinned keys and mode.

`decide(content, kind="call", wait_seconds=None, policy_refusal=None)` returns a `Decision` with `approved`, `outcome` (`"ran"` or `"refused"`), `fp`, `reason`, `record`, `stamp` (the first valid stamp), `witness`, `times`, `catch_up_error` and `misbehaving`. `policy_refusal` journals the attempted call and refuses it without requesting a stamp. `Decision.times` contains nanosecond timestamps and durations for measurement; `times["catch_up_ns"]` is time spent on catch-up after durable approval. The tool starts after `decide` returns. Stamp-wait deadlines and the cooperative catch-up budget do not bound total latency: lock acquisition, canonicalization, signing/verification, journal writes and synchronization can take additional time. No hard wall-clock bound is claimed for a decision.

The step methods in the table above, plus `recover`, `catch_up(wait_seconds=None)`, `settle(seconds)`, `missed(client)`, `drain(seconds)`, `ask_witness(op, index=0, ...)`, `connect(clients)`, `stamps_report()`, `history()` and `close(grace_seconds)` are public.

- `Gate.degraded` is True when a slot has no key, no client or a stopped client. `required_witnesses()` lists the `(role, id)` pairs whose stamps every started call must end with.
- Recovery runs in `Gate.__init__` on a reopened journal. `recover()` after the gate opens raises `GateError`. Recovered approvals and second stamps must name one of the journal's records with the correct sequence and a stamp valid under its pinned keys; no record may be decided twice. Otherwise the gate raises `GateError` and does not start.
- Permission reaches the caller only once approval is durable. A write or sync failure before that raises `GateCrashed`; a failed approval write is not followed by a refusal on the uncertain file. A catch-up failure after durable approval poisons the gate, appears in the returned `Decision.catch_up_error` and `reason`, and makes later operations raise `GateCrashed`. The approval remains valid. `close()` releases resources and raises `GateCrashed` on a poisoned gate; a new gate recovers the journal.
- With two witnesses `give_up` raises `GateError` while a stamp is held for the call; with one witness it is allowed.
- `stamp_arrives(msg, source)` requires `source is req.client` and a valid stamp from the witness pinned in that slot. Unknown (`None`) and wrong sources are rejected without consuming the pending request. `await_stamp` asks the backup at most once per call, however often it is called; `Call.asked` holds the slots asked.
- Request ids are `g<generation>.w<slot>.r<n>`. Each new connection uses a new generation, while a retained client's channel generation, request-id prefix and attempt totals survive replacement of another witness. Ids never repeat across reconnections, regardless of `WitnessClient._ids`. `connect(clients)` fills slots in order, leaves the rest empty and raises on more clients than pins. Pending stamp requests are held in `Gate._requests`.
- Request expiry follows the actual wait deadline, including per-call overrides and the separate backup wait. An unanswered request counts as lost only after its wait ends and a later request in its channel generation has been answered, since witnesses answer in order. Send order, answers and last replies are tracked per gate and channel generation, so a live client reused by a new gate cannot make a new request look older.
- Catch-up asks a channel for a fingerprint in windows of `MAX_ATTEMPTS` (3) requests, with a backoff that adds one wait per retry. An exhausted window is re-armed only when the channel answers a later request validly. An unusable answer (bad signature, another fingerprint or witness, replay or error) excludes that fingerprint on the channel until the same proof of health; after `MAX_BAD_ANSWERS` (2) it is never asked again. Each call gets at most `MAX_TOTAL_REQUESTS` (9) stamp requests per witness channel, including its first request; `MAX_REQUESTS` is a compatibility alias for that total. Unusable answers also identify the witness as misbehaving.
- Maintenance requests share stamp-request send order and channel generation. A verified signed-head response proves channel health and can re-arm retries or prove an expired earlier request lost. Invalid heads provide no valid-health evidence; maintenance requests do not consume stamp retry totals. `ask_witness` matches replies on both witness and request id.
- `settle()` processes queued replies in batches of at most `SETTLE_BATCH` (64), checking its deadline between batches and processing further batches only within its budget. It waits for a reply only while its wait lasts or its channel keeps answering. Requests proven lost are retired, including those for refused calls. A continuous sender cannot trap settlement or close. `drain(seconds)` checks its deadline before each read; `drain(0)` reads nothing. Neither `close()` nor `BenchLedger` calls `drain()`.

`close(grace_seconds)` settles replies, performs catch-up, seals the final decision chain, asks each running witness to save a signed `decision_head`, then captures and verifies terminal signed heads before the owner stops the witnesses. The anchor carries the whole decision chain held in memory. Close compares the decision file on disk with that chain line by line and reports the first difference. Each head request waits at most `max(0.1, wait_seconds)` seconds, apart from synchronous work. Normal close is idempotent and releases the journal locks.

The returned `CloseReport` contains:

- `catch_up_done` and `missing`: whether every started call holds its mode's required stamps, and each call that does not, with the missing witness ids. Stamp completion alone cannot establish complete evidence.
- `signed_heads` and `head_errors`: terminal heads and missing/invalid-head reasons. Retain the heads independently and pass them to `check_run(signed_heads=...)`.
- `decision_heads` and `decision_head_errors`: acknowledged anchors and anchor failures, including a possible `"decision file"` mismatch described under report fields below.
- `misbehaving`: each witness with unusable replies, its role, unusable-reply count, last reason and affected fingerprints. `Decision.misbehaving` lists those received while that call was decided.
- `exhausted`: each approved fingerprint that a required witness's channel will not be asked for again, with witness, requests sent and reason. Pass it to `check_run(exhausted=...)`.

`stamps_report()` returns stamp completion, `misbehaving` and `exhausted` without head capture or closure.

### Checker

`check_run(journal_paths, witness_logs=None, effects_path=None, witness_keys=None, signed_heads=(), catch_up_done=False, *, trusted_keys=None, mode=None, required_witnesses=None, misbehaving=None, exhausted=None)` returns a report and never raises on a bad argument or file. Bad inputs become problems under `by_check.arguments`; malformed domains, noncanonicalizable JSON and evidence read errors also become report problems. `check_run([])` fails because no journal means no evidence. A journal path without a file name (`"/"`, `"."`, `""`) and an invalid mode are argument problems.

Supply independent expected keys, mode (`"one"`, `"both"` or `"failover"`) and required witnesses as `(role, id)` pairs, such as `BenchLedger.required_witnesses()`. Ids alone take their role from their position and count as given without roles. Differences from a journal fail. Save these expected inputs outside the run: `BenchLedger.public_keys()`, `.mode` and `.required_witnesses()`. `witness_keys` is an alias for `trusted_keys`; conflicting aliases fail. Even an empty supplied trust map disables fallback to journal keys. `keys_source` is `"trusted"` or `"journal"`; journal keys always carry an internal-consistency-only note. The checker validates distinct pinned ids and keys, preserves null fixed slots as required roles, and checks each approval and second stamp against its own journal's permitted witnesses.

Give every journal whose decisions a given witness log anchors. A logged or independently supplied authenticated anchor naming no given decision file fails `DecisionHeads`, so checking only one of two journals sharing an anchored witness log fails. `Check3` also requires every journal with a stamped record. Ledger defaults and the approver use separate logs per journal.

`witness_logs` is one path or a list, one log per witness in fixed slot order, main first. Supply every pinned witness's log together with every terminal head. A missing or empty log is bound to its witness by its list position against the journals' fixed slots. A required witness's missing/empty log, or an empty fixed slot, is incomplete evidence if no decision relies on its stamps; otherwise `Rule1` and `Rule2` fail it. `missing_required_logs` lists each with its reason. A size-0 terminal head (64 zeros) with an empty log establishes that the witness stamped nothing. In failover mode the backup is required only for stamps it gave.

| `status` | Meaning |
|---|---|
| `"pass"` | No check fails and the evidence is complete. `ok` is True. |
| `"pass_incomplete_evidence"` | No check fails, but evidence is missing. `ok` is False and `unmeasured` explains each gap. |
| `"fail"` | At least one check fails. `ok` is False and `problems` lists the failures. |

Complete evidence requires an effects file; independently supplied keys, mode and required witnesses with roles; all required logs and their retained terminal heads; decision anchors covering the required chains and their pre-restart prefixes; matching effects for every approval; and either `catch_up_done=True` or no missing stamp. With no witness configured or required, the status is never `"pass"`: `unmeasured` contains `"no witnesses"`. `unmeasured` entries have `input` and `reason`, plus details where applicable. `time_checks` describes timestamp ordering only; synchronization completion and drive durability are unmeasured.

With effects checked, an approval without a matching effect makes evidence incomplete, with `"approvals without effect"` and affected fingerprints under `unmeasured`. An absent effects file counts as empty when no record was approved, since tools create it on their first execution. An effect for a refused record is reported under `RefusedNeverRuns` even if its other fields are malformed. Fingerprints supplied through `exhausted=CloseReport.exhausted` make evidence incomplete under `"exhausted"`, rather than failing `StampsComplete`. `misbehaving=CloseReport.misbehaving` populates `misbehaving_witnesses` with a note; this alone is not a problem, because unusable replies do not count as stamps.

The report also contains `by_check`, `notes`, `calls_missing_stamps`, `only_one_witness_holds` and `counts`. The checks and their comparisons are listed above.

From the command line:

```sh
python -m witnessed_gate.checker JOURNAL --witness-log LOG --effects FILE \
  --key ID=HEX --mode one --required-witness main=ID --signed-heads HEADS.jsonl \
  --catch-up-done
```

Repeat journals, `--witness-log`, `--key` and `--required-witness` as needed, main first; use `backup=` for an empty slot. `--signed-heads FILE` reads terminal heads as JSON lines. Exit codes are 0 for `"pass"`, 2 for `"pass_incomplete_evidence"`, 1 for `"fail"` and 3 for usage errors such as `--key` without `=`.

### Decision evidence report fields

An `unmeasured` entry with `input` equal to `"decision heads"` also carries `journal` (the record file's name), `witness` (null for an empty slot) and `count` (the number of decision lines covered). With no matching anchor from that witness, `count` is the whole chain length and `lines` is absent. Otherwise `lines` is `[first, last]`, the zero-based inclusive decision-line range after that witness's longest matching anchor. An entry for lines before a restart also carries `restart_line`, the restart line's index, with `lines` and `count` for the lines the witness never anchored before that restart.

`CloseReport.decision_head_errors` maps witnesses that did not acknowledge a valid anchor to their reasons. It may also contain `"decision file"` when the file on disk differs from the chain held in memory at close; that reason identifies the first differing line.

Every anchor in any given witness log is compared with the decision chain at its own length, whether that witness is required or not. An authenticated `decision_head` supplied in `signed_heads` receives the same comparisons but adds no logged anchor or retained terminal head. A mismatch, excessive length or unmatched journal identity fails `DecisionHeads`. Lines after a required witness's longest anchor are incomplete evidence; the same applies to a failover backup whose stamp a decision holds.

For each restart at decision-line index r, let a be the length of that witness's longest anchor of at most r signed before the restart's `wall_ns` (0 if none). If a < r, decision lines a through r-1 go under `unmeasured`, with witness, restart line, range and count. A clean close followed by a reopen puts the restart at the prior anchor's length and adds no gap. An honest crash and restart is incomplete evidence. Anchors made at or after a restart still receive chain comparisons and count towards coverage through the longest anchor, but do not establish pre-restart coverage; see deviation 13 for the clock assumption and remaining limit.

### Effects and execution identity

`witnessed_gate.wire` provides `effect_line(record)`, `unbound_effect_line`, `effect_for_call(function, arguments, registry, *, execution_id)`, `ApprovedCalls`, `record_action`, `args_sha256` and `EFFECT_FIELDS`. Each gate owns its `approved_calls` registry. A supplied registry binds exclusively to one gate and cannot be reused across gates. `tests/unit/helpers.py`'s `call()` writes version 2 effects lines.

Effects are matched by `record_fp`, with one execution per approval, a unique 32-character lowercase-hex `exec_id`, and exact `function` and `args_sha256` (sha256 of canonical JSON arguments). Missing/null `record_fp`, repeated execution ids, repeated approval use and action mismatches fail. `record_action` takes `function` and `arguments` from Inspect records, or `action_kind` and `handover` from bench records.

Instrumentation consumes an approval only for the framework execution identity and exact action. Inspect uses the tool call's own `id` from its execution observer; `BenchLedger` uses `.call_id` on the record returned by `write()`. Model arguments never supply that identity. The binding depends on unique identities. The approver journals and refuses empty or previously presented ids, revoking any waiting approval so a later execution under that id writes an unbound line. A bench courier must pass `effect_line` the record of the delivery it is making: supplying an earlier undelivered record consumes that record's approval.

`ApprovedCalls.claim(id)` returns a token for a new identity, or None if it was already presented, approved or revoked. `add(record, token=None)` returns False without registering if the identity was revoked or the token does not match its claim. Claimed identities require the exact token, including when no token is supplied; unclaimed bench identities permit tokenless registration. `revoke(id)` withdraws the waiting approval and permanently invalidates the identity; `seen(id)` checks without claiming. Claim, decision and registration use that token, so an approval decided while a duplicate id arrived cannot register after revocation. The approver rejects that call with `metadata["outcome"] = "revoked"`, leaving the approval journaled without an effect.

### Inspect approver

`witnessed_gate_approver(journal, witness_dir=None, wait_seconds=2.0, backup_witness_dir=None, witness_mode=None, witness_faults=None, backup_faults=None, operator=..., full_fsync=False, registry=None)` is installed with `eval(..., approval=[ApprovalPolicy(approver, "*")])`. It adds approved records to the gate's registry or a gate-exclusive `registry=`. Tools receive that registry explicitly. It preserves `[None, backup]` when only a backup directory is configured, in either mode.

A record's `call_id` and `tool_call_id` are Inspect's own tool-call id. A `call_id` among the tool's arguments stays only in `arguments`; the demo uses framework ids such as `tc-c1` for an argument id `c1`. Install `inspect_approver.execution.install_execution_identity()` in the active sample before tools run, as the demo's first solver does. `current_call_id()` reads the id through Inspect's per-sample observer, with task-local context for concurrent execution.

Before rejecting a call because a sentinel monitors tool calls, the approver journals the attempted call and its policy refusal under the gate lock. If the sentinel check raises, it journals and refuses the call in the same way. Empty or repeated ids are also refused before normal stamp decisions. The approver refuses installation on an Inspect version without a way to detect active sentinels. On `GateCrashed`, it rejects with `metadata["outcome"] = "crashed"`; post-approval catch-up failures are included in approval metadata.

`close_gates(grace)` closes every gate and stops every witness even when some fail. It returns `{journal path: CloseReport}` on clean closure, otherwise raises `CloseGatesError`. The exception's `reports` contains all reports; `errors` maps journal paths to lists of every failure as `{"operation": "close" or "stop", "client": witness id or None, "error"}`.

The demo supports `--witness on|off`, `--backup on|off`, `--witness-mode both|failover`, `--main-fault MODE`, `--wait S`, `--calls id:function[:argument_call_id]` and the test hook `--pretend-sentinel`.

### Journal and witness

A journal takes exclusive locks on both resolved evidence paths (record and decision file, each with `.lock` appended), in sorted order before reading either. It holds them until `journal.close()`. Another owner sharing either stream raises `JournalError` (`"another gate owns this journal"`); failed acquisition releases locks already taken. `run` and `run.jsonl` therefore cannot concurrently own their shared decision stream.

`JournalFailed`, a `JournalError`, is raised by an append during or after a failed write or sync. `Journal.write_record` raises `JournalError` for non-JSON input before computing its fingerprint. `Gate.decide` instead journals a stand-in and refuses the attempted call without raising: each non-JSON field becomes `{"not_json": repr}`. Keys and values are checked. If that still is not JSON, the whole content becomes `{"not_json": an ASCII repr}`; a non-JSON action kind is replaced similarly, so the record and refusal can be journaled.

Run a witness with `python -m witnessed_gate.witness --state-dir DIR [--full-fsync]`. It writes `hello` with `witness`, `pubkey`, `size`, `head` and `full_fsync`, then answers `stamp`, `head`, `decision_head`, `proof` and `consistency` requests. Replies carry the request's `id`; `bye` or end of stdin stops it. `WitnessClient.launch(state_dir, faults=None, full_fsync=False)` starts one and exposes `pubkey`, `witness_id`, `send`, `next_message(timeout)` (until a gate attaches it), `alive`, `stop()` and `kill()`. Enabling `full_fsync` passes `--full-fsync`.

A witness takes an exclusive `flock` on `DIR/lock` for its lifetime. A second process on that folder writes `{"op": "refused", "error": ...}` and exits; `WitnessClient.launch` raises `WitnessGone("the witness did not start: another witness process owns this state folder: ...")`. Stop or kill a witness, and let `kill()` wait for it, before starting another on the same folder. The `outage` fault releases its lock before exiting.

A witness refuses startup if a log line has another key's signature, names another witness or repeats a fingerprint, or if `witness.json` names another key. A log-write failure makes every later stamp request return an error. Reopening validates and syncs recovered state at the requested `full_fsync` setting before serving stamps or heads; failed sync prevents startup. Recovered-state sync narrows the uncertainty window but does not prove that bytes from an earlier failed write reached the drive, including under Linux writeback behaviour. The witness process's startup refusal through `WitnessClient.launch` has no dedicated test.

`WitnessClient.send` uses a nonblocking queue with capacity 64 per witness and at most one in-flight pipe write. It returns False on overflow; shutdown does not wait for queue capacity. An instance-level `send` override remains supported. `answered` and `last_answer` expose reply activity, and `last_send_error` holds a refused send's reason, which appears in a refusal, such as `"the witness's send queue is full"`.

Fault hooks shared by tests and the bench use `WitnessClient.launch(dir, faults={"mode": M, "delay": S, "after": N, "journal": PATH})`. Modes are `slow`, `drop`, `outage`, `malformed`, `replay`, `wrong-key`, `wrong-fp`, `memory-only` and `observe`; the fault starts after N good stamps.

### Bench ledger

`BenchLedger(run_dir, run_id, wait_seconds=2.0, witness_faults=None, refusal_error=GateRefused, witness_dir=None, backup=False, backup_witness_dir=None, backup_faults=None, witness_mode=None, close_grace_seconds=0.0, ...)`, or `make_ledger(run_dir, run_id, choices, **options)`, starts witness processes per ledger. Witness folders default to `run_dir/witness/<run_id>/` and `run_dir/witness_backup/<run_id>/`. An explicit `witness_dir` may be shared only by ledgers that run one at a time. `full_fsync=True` reaches both witnesses.

`write(record)` accepts a compatible `Record` or dict and returns a `WrittenRecord`, a dict with the journal fields and `receipt` holding the first valid stamp. A refusal raises `refusal_error` (the bench supplies its `LedgerError`) with the gate's reason. Framework metadata is held as attributes so `record_fingerprint(returned) == returned["fp"]`: `.call_id` is the record fingerprint, `.gate_decision` is the complete `Decision`, and `.catch_up_error` exposes post-approval failure. Supplied call ids cannot choose the framework identity. `effect_line(returned)` consumes that gate's approval for the exact identity and action once. Pre-approval `GateCrashed` propagates; post-approval catch-up failure is exposed on the returned record.

`records()` returns all written records, refused ones included, in journal order with receipts. `records()` and `outcomes()` each use `Gate.history()` to read records and decisions under the shared lock as one consistent snapshot, including after normal closure or reopening. `outcomes()` lists journaled records only, with `outcome` None for an undecided record. Other interfaces are `witness_pubkey`, `witness_keys`, `witness_logs`, `journal_path`, `decisions_path`, `public_keys()`, `required_witnesses()`, `mode`, `degraded`, `signed_heads` and `close()`.

`public_keys()` supplies hello keys, main first, for `trusted_keys`. `required_witnesses()` supplies `(role, id)` pairs from the ledger's configuration and witness hello lines, never from the journal; a witness that did not start has id None. `mode` is `"one"`, `"both"` or `"failover"`. A ledger configured for two witnesses retains both slots when one fails to start and reports `degraded`; the backup never replaces the main slot. During the run, `degraded` reflects missing witnesses; after `close()` it retains the value captured when close began, before witnesses were stopped.

`close()` captures final heads before stopping witnesses and returns the gate's `CloseReport`; `ledger.signed_heads` exposes those heads afterward. A poisoned close releases resources and raises `GateCrashed`. A check without the bench's effects file has incomplete evidence, with `effects` in `unmeasured`.

The compatible receipt checker expects `record_fp` and `mac` in witness logs and cannot read this log format; use `checker.check_run` for witness evidence. When multiple journals intentionally share one witness log, pass them all so `Check3` sees every record and `DecisionHeads` sees every anchored chain.

## Inspect 0.3.291 integration details

- The approver is the only one, applied to every tool with `eval(..., approval=[ApprovalPolicy(approver, "*")])`. Eval-level policy is set first; task policy applies only when none is active (`_eval/context.py`, `init_task_context`). `"*"` contains a glob character, so `fnmatch` matches every tool name (`approval/_policy.py`; its `arguments` field is unused here). The demo log records one policy, `witnessed_gate` for `"*"`, and one approval event per tool call.
- `react(submit=False)` receives no `approval=` argument, which would replace the active policy inside the agent (`agent/_react.py`). The script ends with a plain answer.
- Inspect refuses an `"approve"` if the approver changed the call in place (`model/_call_tools.py`). The approver deep-copies arguments for journaling.
- A sentinel runs after approvers and may change call arguments; Inspect then runs the changed call without another approval (`model/_call_tools.py`: `sentinel_before_tool_call`, then `revalidated_tool_call`). A stamp would cover a different call. The approver therefore rejects calls while a sentinel watches tool calls or its stages cannot be read. It uses private `active_sentinel()` (`_sentinel/_context.py`) and `_watches(BeforeToolCall)` (`_sentinel/_dispatch.py`). Inside the approver's `"final"` sentinel scope (`approval/_apply.py`), public `checks_tool_calls()` returns False and cannot detect this. If the optional `inspect_sentinel` package is absent, `_sentinel/_dispatch.py` cannot be imported; the approver conservatively treats any active sentinel as watching tool calls. `--pretend-sentinel` exercises that rejection.
- Time in an approver counts as waiting: `apply_tool_approval` runs it under `suspend_limits`. Gate waits limit stamp waiting, not total latency.
- Without usage metadata, the mock model counts tokens with tiktoken, which may fetch an encoding file over the network. Every scripted output supplies `ModelUsage`, avoiding that fetch and keeping tests offline.
